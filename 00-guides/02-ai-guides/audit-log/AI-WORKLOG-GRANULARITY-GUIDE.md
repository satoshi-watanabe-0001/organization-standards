# 監査ログの単位・粒度ガイドライン

**目的**: AIの推論プロセス評価を最適化するための監査ログ分割基準の確立

---

## セクション1: 基本概念と原則

### 1.1 監査ログ単位の主目的

本ドキュメントで定義する監査ログ単位（1セッション）は、以下の**推論評価**に特化した目的を持つ：

- ✅ **推論の正確性検証**: AIの論理展開が適切かどうかの判定
- ✅ **推論変化の追跡**: 作業中に考えが変わった箇所とその理由の記録
- ✅ **推論一貫性の評価**: 前提条件から結論まで論理的な整合性の確認
- ✅ **推論品質の向上**: 過去の推論パターンからの学習と改善

### 1.2 基本原則

**核心原則**: **1つの推論コンテキスト = 1つの監査ログ（1セッション）**

#### 推論コンテキストの定義
推論コンテキストとは、以下の条件を満たす範囲：

1. **同じ前提条件・制約条件**で推論を行う
2. **意思決定が相互に依存**している
3. **推論の結果が後続の推論に直接影響**を与える
4. **同じ評価基準**で推論の妥当性を判定できる

#### 分割・統合の判断軸

| 条件 | 判断 | 理由 |
|------|------|------|
| 推論が**独立**している | 分割 | 各推論を独立して評価可能 |
| 推論が**連続・依存**している | 統合 | 推論の流れを保持して評価 |
| 前提条件が**変化**する | 分割 | 異なるコンテキストでの推論評価 |
| 評価観点が**異なる** | 分割 | 専門的な評価が必要 |

## セクション2: 監査ログ分割の判断基準

### 2.1 分割すべきケース（具体例）

#### A. 要求仕様書の異なるユースケースごと

**例**: ECサイトの要求仕様書
- **監査ログ1**: ユーザー登録・認証機能
- **監査ログ2**: 商品検索・表示機能  
- **監査ログ3**: 購入・決済機能

**理由**: 各ユースケースで異なるビジネス要件と技術制約による推論

#### B. アーキテクチャレイヤーごと

**例**: 3層アーキテクチャシステム
- **監査ログ1**: プレゼンテーション層（UI設計・ユーザビリティ推論）
- **監査ログ2**: ビジネスロジック層（業務要件・ルール推論）
- **監査ログ3**: データアクセス層（データ構造・パフォーマンス推論）

**理由**: 各層で専門性と評価観点が大きく異なる

#### C. 異なる技術選定が必要な場合

**例**: マイクロサービス開発
- **監査ログ1**: フレームワーク選定（技術比較・選定推論）
- **監査ログ2**: データベース設計（データモデリング推論）
- **監査ログ3**: API連携実装（インターフェース設計推論）

**理由**: 技術領域ごとに専門知識と推論パターンが異なる

#### D. 推論の前提条件が変わる場合

**例**: 段階的リリース計画
- **監査ログ1**: MVP版実装（最小機能セット前提）
- **監査ログ2**: 本格版実装（フル機能セット前提）

**理由**: 前提条件の変化により推論の妥当性評価が変わる

#### E. 独立してレビュー・評価できる単位

**例**: セキュリティ要件
- **監査ログ1**: 認証システム（セキュリティ専門家による評価）
- **監査ログ2**: 業務ロジック（ビジネスアナリストによる評価）

**理由**: 評価者の専門性に応じた独立した評価が必要

### 2.2 統合すべきケース

#### A. 密接に関連し、推論が相互に影響する作業

**例**: データベース最適化
```
【統合パターン】
クエリ最適化 → インデックス設計 → テーブル構造調整
（連続した推論で、各ステップが次に影響）
```

#### B. 同一の意思決定プロセスで完結する作業

**例**: APIエンドポイント設計
```
【統合パターン】
要件分析 → URL設計 → パラメータ設計 → レスポンス設計
（一つの意思決定フローで完結）
```

#### C. 分割すると推論の流れが追えなくなる作業

**例**: バグ修正
```
【統合パターン】
現象調査 → 原因特定 → 修正方針決定 → 実装 → テスト
（推論の連続性が評価の鍵）
```

## セクション3: 推奨される粒度レベル

### 3.1 小粒度（強く推奨）

| 項目 | 基準 |
|------|------|
| **作業時間** | 2-8時間 |
| **推論の深さ** | 1-3段階の意思決定 |
| **意思決定ポイント** | 1-5個 |
| **成果物** | 1-3個のファイル/モジュール |
| **推論変化** | 0-2回の方針転換 |

**メリット**:
- ✅ 推論の評価が容易で精密
- ✅ 問題箇所の特定が迅速
- ✅ 推論変化の理由が明確
- ✅ レビュー負荷が適切

**適用例**:
- 単一APIエンドポイントの実装
- 特定画面のUI実装
- データベーステーブル設計
- 特定アルゴリズムの実装

### 3.2 中粒度（条件付き許可）

| 項目 | 基準 |
|------|------|
| **作業時間** | 1-2日 |
| **推論の深さ** | 3-5段階の意思決定 |
| **意思決定ポイント** | 5-10個 |
| **成果物** | 1つの機能単位 |
| **推論変化** | 2-4回の方針転換 |

**適用条件**:
- 推論が密接に関連している
- 推論の中間結果が次のステップに必要
- 分割すると評価の文脈が失われる

**注意事項**:
- 推論の各段階を明確に記録
- 中間での推論変化を詳細に記録
- 定期的な推論一貫性チェック

### 3.3 大粒度（非推奨・分割必須）

| 項目 | 基準 |
|------|------|
| **作業時間** | 3日以上 |
| **問題点** | 推論の評価が困難、問題箇所の特定が困難 |
| **対策** | **必ず分割する** |

**分割が必要な理由**:
- 推論の複雑さが評価者の認知負荷を超える
- 推論変化の追跡が困難
- 問題発生時の原因特定に時間がかかる
- レビュー品質が低下する

## セクション4: 具体的な分割例とケーススタディ

### 4.1 例1: Web API開発の要求仕様書

#### 要求仕様書の内容
```
ユーザー管理システムのREST API開発
- ユーザー登録・認証機能
- ユーザープロフィール管理
- 管理者権限機能
- ログ出力・監査機能
```

#### 分割案

**監査ログ1**: API設計・仕様策定
- **推論コンテキスト**: REST設計原則、URL構造、HTTP方式選定
- **時間**: 4-6時間
- **主な意思決定**: エンドポイント設計、リクエスト/レスポンス形式
- **成果物**: API仕様書、OpenAPI定義

**監査ログ2**: 認証・認可システム実装
- **推論コンテキスト**: セキュリティ要件、認証方式選定、トークン管理
- **時間**: 6-8時間
- **主な意思決定**: JWT vs セッション、権限モデル設計
- **成果物**: 認証モジュール、ミドルウェア

**監査ログ3**: ビジネスロジック実装
- **推論コンテキスト**: 業務要件、データ処理ロジック、バリデーション
- **時間**: 8-12時間（分割可能）
- **主な意思決定**: バリデーション方式、エラーハンドリング
- **成果物**: サービスクラス、ビジネスルール実装

**監査ログ4**: データアクセス層実装
- **推論コンテキスト**: データモデル、パフォーマンス、データ整合性
- **時間**: 4-6時間
- **主な意思決定**: ORM使用、クエリ最適化、トランザクション設計
- **成果物**: リポジトリ実装、データベーススキーマ

#### 分割理由の分析

| 分割単位 | 推論の独立性 | 評価観点 | 専門性 |
|---------|-------------|---------|-------|
| API設計 | 高（他に依存しない） | REST設計品質 | API設計 |
| 認証実装 | 高（独立したセキュリティ要件） | セキュリティ品質 | セキュリティ |
| ビジネスロジック | 中（API設計に依存） | 業務要件適合性 | ドメイン知識 |
| データアクセス | 中（ビジネスロジックに依存） | データ品質・性能 | データベース |

### 4.2 例2: バグ修正タスク

#### バグ報告
```
ユーザー登録後、メール送信が間欠的に失敗する
エラーログには断続的にタイムアウトエラーが記録される
```

#### 統合案（推奨）

**監査ログ1**: バグ調査・修正・検証（統合）
- **推論コンテキスト**: 問題現象から原因特定、修正方針、実装、検証
- **時間**: 4-8時間
- **推論の流れ**:
  ```
  現象分析 → ログ調査 → 仮説構築 → 原因特定 → 
  修正方針決定 → 実装 → テスト → 効果確認
  ```

#### 統合理由
- 推論が連続的で相互依存している
- 原因調査の結果が修正方針に直接影響
- 分割すると推論の文脈が失われる
- 一つの問題解決プロセスとして評価すべき

### 4.3 例3: 大規模機能開発（分割必須ケース）

#### 要求仕様書
```
オンライン学習システムの開発
- ユーザー管理（学生・教師・管理者）
- コース管理（作成・編集・公開）
- 学習進捗管理
- 評価・採点システム
- レポート・分析機能
```

#### 分割戦略

**Phase 1**: 機能単位での分割
```
監査ログ1: ユーザー管理システム
監査ログ2: コース管理システム  
監査ログ3: 学習進捗管理システム
監査ログ4: 評価・採点システム
監査ログ5: レポート・分析システム
```

**Phase 2**: 各機能をさらに技術層で分割
```
監査ログ1-1: ユーザー管理 - データモデル設計
監査ログ1-2: ユーザー管理 - API実装
監査ログ1-3: ユーザー管理 - フロントエンド実装
```

#### 分割の推論
1. **複雑性の管理**: 全体では推論が複雑すぎて評価困難
2. **専門性の分離**: UI設計、ビジネスロジック、データベース設計で異なる専門性
3. **並列評価**: 各監査ログを独立してレビュー可能
4. **段階的な品質保証**: 各段階で推論品質を確保

## セクション5: 監査ログ間の関連付け

### 5.1 階層構造の定義

#### 親監査ログ（Parent Worklog）
- **役割**: 全体の推論の枠組み・方針を定義
- **内容**: 要求分析、全体設計、技術選択の大方針
- **期間**: 通常1-2日
- **成果物**: 設計書、技術選択根拠、全体方針書

#### 子監査ログ（Child Worklog）
- **役割**: 具体的な実装レベルの推論を記録
- **内容**: 詳細設計、実装、テストの推論
- **期間**: 通常2-8時間
- **成果物**: 実装コード、テストコード、詳細ドキュメント

### 5.2 メタデータでの関連付け

#### 基本的な関連付け
```yaml
---
# 子監査ログのメタデータ例
worklog_id: CHILD-001
parent_worklog_id: PARENT-001
related_worklog_ids: [CHILD-002, CHILD-003]
sequence_number: 1
dependency_type: sequential  # sequential | parallel | conditional
---
```

#### 関連性の種類
| 関連性タイプ | 説明 | 例 |
|------------|------|---|
| **Sequential** | 順次実行（前の監査ログの結果が次に必要） | 設計→実装→テスト |
| **Parallel** | 並列実行（独立して実行可能） | 複数APIの並列開発 |
| **Conditional** | 条件分岐（前の結果により実行が決定） | A/Bテストの結果による実装 |

#### 依存関係の記録
```yaml
# 複雑な依存関係の例
dependencies:
  - worklog_id: DESIGN-001
    type: "prerequisite"
    description: "API設計の完了が必要"
  - worklog_id: AUTH-001  
    type: "integration_point"
    description: "認証システムとの連携が必要"
```

## セクション6: 推論評価の観点と品質基準

### 6.1 推論評価チェックリスト

#### 基本的な推論品質
- [ ] **前提条件の明確性**: 推論の出発点が明確に記載されている
- [ ] **論理的整合性**: 推論の各ステップが論理的に妥当
- [ ] **結論の妥当性**: 前提から結論への論理展開が適切
- [ ] **不確実性の認識**: 推論の限界と不確実な部分を明示
- [ ] **確信度の記録**: 各判断の確信度が適切に記録されている

#### 推論プロセスの透明性
- [ ] **選択肢の網羅**: 検討した選択肢が適切に列挙されている
- [ ] **判断基準の明示**: 意思決定の基準が明確
- [ ] **トレードオフの分析**: 利害得失が適切に分析されている
- [ ] **リスク評価**: 潜在的なリスクが適切に識別・評価されている
- [ ] **代替案の検討**: 主案以外の選択肢も適切に検討されている

#### 推論の変化追跡
- [ ] **変更点の明示**: 推論が変わった箇所が明確に記録
- [ ] **変更理由の記録**: なぜ推論を変えたのか理由が明確
- [ ] **影響範囲の分析**: 変更が他の推論に与える影響を評価
- [ ] **一貫性の検証**: 変更後も全体として論理的に一貫している
- [ ] **学習の記録**: 推論変更から得られた学習が記録されている

### 6.2 品質レベルの定義

#### レベル1: 基本品質（最低限）
- 推論の基本的な流れが記録されている
- 主要な意思決定の理由が記載されている
- 結論と根拠の対応が明確

#### レベル2: 標準品質（推奨）
- 複数の選択肢と評価基準が記載されている
- 推論の不確実性とリスクが適切に評価されている
- 推論の変更履歴が適切に管理されている

#### レベル3: 高品質（理想）
- 推論プロセスが詳細に可視化されている
- 定量的な評価基準と根拠が充実している
- 推論パターンの再利用可能性が高い

## セクション7: ベストプラクティスとアンチパターン

### 7.1 推奨される作業の進め方

#### ステップ1: 要求分析と推論コンテキスト分析
```
1. 要求仕様書を詳細に分析
2. 推論が必要な領域を特定
3. 推論の独立性・依存性を分析
4. 適切な監査ログ分割案を作成
```

#### ステップ2: 監査ログ計画の作成
```
1. 各監査ログの推論コンテキストを定義
2. 監査ログ間の関連性を明確化
3. 推論評価の観点を設定
4. レビュー・評価の責任者を指定
```

#### ステップ3: 推論プロセスの記録
```
1. 推論の前提条件を明確に記録
2. 推論の各ステップを詳細に記録
3. 推論の変化があれば即座に記録
4. 定期的な一貫性チェックを実施
```

#### ステップ4: 推論評価とフィードバック
```
1. 作業完了後、推論の妥当性を評価
2. 推論品質の改善点を特定
3. 学習事項を次回作業に活用
4. 推論パターンをナレッジベース化
```

### 7.2 避けるべきアンチパターン

#### ❌ アンチパターン1: 推論の詰め込み
**問題**: 1つの監査ログに複数の独立した推論を詰め込む

**例（悪い例）**:
```
監査ログ: システム全体開発
- API設計の推論
- データベース設計の推論  
- フロントエンド設計の推論
- セキュリティ設計の推論
```

**問題点**:
- 推論コンテキストが混在して評価困難
- どの推論に問題があるか特定が困難
- レビュー負荷が過大

**改善方法**:
各推論コンテキストを独立した監査ログに分割

#### ❌ アンチパターン2: 推論の途中分割
**問題**: 推論プロセスの途中で監査ログを分割

**例（悪い例）**:
```
監査ログ1: 要件分析と技術選択の一部
監査ログ2: 技術選択の残りと設計の一部
監査ログ3: 設計の残りと実装
```

**問題点**:
- 推論の文脈が分断される
- 意思決定プロセスが追跡困難
- 評価時に複数のログを参照する必要

**改善方法**:
推論の完結する単位で監査ログを分割

#### ❌ アンチパターン3: 関連性無視の分割
**問題**: 推論の関連性を無視した機械的分割

**例（悪い例）**:
```
監査ログを時間ベースで分割
- 監査ログ1: 1日目の作業
- 監査ログ2: 2日目の作業
- 監査ログ3: 3日目の作業
```

**問題点**:
- 推論の論理的なまとまりが無視される
- 関連する推論が分散される
- 評価時に全体像が把握困難

**改善方法**:
推論の論理的な関連性に基づいた分割

監査ログの分割は**推論コンテキスト**を基準とする。
詳細は「WORKLOG-GRANULARITY-GUIDE.md」を参照。

**基本原則**: 1つの推論コンテキスト = 1つの監査ログ（1セッション）

**分割判断**:
- 推論が独立 → 分割
- 推論が連続・依存 → 統合
- 前提条件変化 → 分割

### 8.3 品質チェックスクリプトの提案

#### 粒度チェックスクリプト例
```bash
#!/bin/bash
# worklog_granularity_check.sh

check_worklog_granularity() {
    local worklog_file=$1
    
    # 時間範囲チェック
    duration=$(extract_duration "$worklog_file")
    if [ "$duration" -gt 48 ]; then
        echo "WARNING: $worklog_file の作業時間が48時間を超えています"
        echo "推奨: 監査ログを分割してください"
    fi
    
    # 推論深度チェック
    depth=$(grep "inference_depth:" "$worklog_file" | cut -d: -f2 | tr -d ' ')
    if [ "$depth" -gt 5 ]; then
        echo "WARNING: $worklog_file の推論深度が5を超えています"
        echo "推奨: 推論コンテキストを分割してください"
    fi
    
    # 関連ファイル数チェック
    file_count=$(grep -c "成果物:" "$worklog_file")
    if [ "$file_count" -gt 5 ]; then
        echo "INFO: $worklog_file で多数のファイルが作成されています"
        echo "確認: 推論コンテキストが適切に統合されているか"
    fi
}
```

## 付録: クイックリファレンス

### A.1 粒度判定フローチャート

```
作業要求を受領
    ↓
推論コンテキストを分析
    ↓
推論は独立しているか？
    ├─ Yes → 分割検討
    └─ No → 統合検討
         ↓
作業時間は8時間以下か？
    ├─ Yes → 1つの監査ログ
    └─ No → 分割必須
```

### A.2 推論コンテキスト判定表

| 判定項目 | 同じコンテキスト | 異なるコンテキスト |
|---------|----------------|------------------|
| **前提条件** | 同じ要件・制約 | 異なる要件・制約 |
| **意思決定** | 相互に依存 | 独立して決定可能 |
| **専門性** | 同じ技術領域 | 異なる技術領域 |
| **評価観点** | 同じ品質基準 | 異なる品質基準 |
| **成果物** | 密接に関連 | 独立して利用可能 |

### A.3 緊急時の判断指針

推論コンテキストが不明確な場合：
1. **小粒度優先**: 迷った場合は小さく分割
2. **独立性重視**: 評価が独立してできるかを基準
3. **時間制限**: 8時間を超える場合は必ず分割
4. **専門性考慮**: 異なる専門分野なら分割
