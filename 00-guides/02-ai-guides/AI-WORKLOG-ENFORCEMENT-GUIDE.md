> 🚨 **【必須】作業開始前の絶対条件**
> 
> **すべてのAIエージェントは作業開始前に必ず以下を実行すること:**
> 1. ユーザーに作業ログ保存先を確認・指定してもらう
> 2. 3段階STOP-GATEシステムを完全実行
> 3. 作業ログファイルの作成と初期記録完了
> 
> **作業ログなしでの作業開始は組織標準違反です。**

## セクション1: 概要と目的

### 1.1 作業ログが重要な理由

作業ログは単なる記録ではなく、以下の重要な価値を提供する：

- **透明性の確保**: 思考プロセスと意思決定の根拠を明確化
- **品質保証**: 作業の抜け漏れ防止と継続的改善の基盤
- **トレーサビリティ**: 問題発生時の原因追跡と対策立案
- **知識蓄積**: 組織全体の開発ノウハウの体系化
- **リスク管理**: 潜在的問題の早期発見と予防措置

### 1.2 作業ログ未作成の重大な結果

作業ログを作成せずに作業を進めた場合、以下の深刻な問題が発生する：

| 問題カテゴリ | 具体的な影響 | ビジネスインパクト |
|------------|------------|-----------------|
| **品質低下** | レビュー不可能、バグ混入リスク増大 | 顧客満足度低下、信頼失墜 |
| **作業効率悪化** | 重複作業、手戻り発生 | コスト増、納期遅延 |
| **ナレッジロス** | 暗黙知の散逸、再現性なし | 技術的負債蓄積 |
| **コンプライアンス違反** | 監査対応不可、説明責任果たせず | 法的リスク、契約違反 |

### 1.3 適切な作業ログ記録のメリット

- ✅ **迅速な問題解決**: 過去の判断根拠から効率的にデバッグ可能
- ✅ **高品質な成果物**: 体系的な思考プロセスによる設計品質向上
- ✅ **チーム連携強化**: 他メンバーとの情報共有とコラボレーション促進
- ✅ **継続的改善**: データに基づいた開発プロセスの最適化

### 1.4 作業ログの単位・粒度

作業ログの分割は**推論コンテキスト**を基準とします。

**基本原則**: 1つの推論コンテキスト = 1つの作業ログ

**分割判断の基準**:
- 推論が独立している → **分割**
- 推論が連続・相互依存している → **統合**
- 前提条件が変化する → **分割**
- 評価観点が異なる → **分割**

**推奨粒度**:
- 作業時間: 2-8時間（小粒度推奨）
- 推論深度: 1-3段階の意思決定
- 成果物: 1-3個のファイル/モジュール

**詳細な分割基準とベストプラクティスは以下を参照**:
→ [AI-WORKLOG-GRANULARITY-GUIDE.md](./AI-WORKLOG-GRANULARITY-GUIDE.md)

**重要**: 
- 3日以上かかる作業は必ず分割してください
- 1つの要求仕様書が複数の作業ログに分かれることは推奨されています
- 推論の評価可能性を最優先に考えてください

## セクション2: 作業開始前の必須チェック（STOP-GATE方式）

### 🛑 3段階ゲートシステム（全ステップクリア必須）

#### **GATE 1: 作業ログ保存先の確認・指定**

**❗ 重要: 保存先は固定されていません。必ずユーザーに確認してください。**

**必須実行手順:**
1. **ユーザーに保存先を質問**
   ```
   「この作業の作業ログをどこに保存しますか？
   以下のような選択肢があります：
   - プロジェクト専用フォルダ
   - 機能別フォルダ  
   - 日付別フォルダ
   - その他ご指定の場所
   具体的なパスを教えてください。」
   ```

2. **保存先の種類例**
   - **プロジェクト別**: `/projects/project-alpha/worklogs/`
   - **機能別**: `/features/user-auth/logs/`
   - **日付別**: `/worklogs/2026/02/`
   - **AI Drive**: `/organization-standards/11-worklogs/YYYY/MM/`
   - **リポジトリ内**: `./docs/worklogs/`
   - **一時作業用**: `/temp/current-task/`

**検証項目:**
- [ ] ユーザーから明確な保存先パスを取得した
- [ ] 指定されたディレクトリが存在するか確認した
- [ ] 書き込み権限があることを確認した
- [ ] ディスク容量に問題がないことを確認した

**失格条件:** 保存先が「未定」「後で決める」「仮置き」の場合は**作業開始禁止**

#### **GATE 2: 作業ログファイルの作成**

**検証項目:**
- [ ] ユーザー指定の保存先に移動した
- [ ] 組織標準テンプレートを使用してファイルが作成されている
- [ ] ファイル名が命名規則に従っている: `worklog_YYYYMMDD_HHMMSS_[TASK-ID]_[brief-desc].md`
- [ ] ファイルが実際に指定パスに保存されている
- [ ] ファイルが読み書き可能である

**失格条件:** ファイルが物理的に存在しない場合は**作業開始禁止**

#### **GATE 3: 初期情報の記録**

**検証項目:**
- [ ] 作業ID、作業名、開始時刻が記録されている
- [ ] 作業目的と要件理解が記述されている
- [ ] 参照ドキュメントがリストアップされている
- [ ] 初期想定と前提条件が明記されている
- [ ] 保存先パスがメタデータに正確に記録されている

**失格条件:** 必須項目が空欄の場合は**作業開始禁止**

### ゲート突破確認宣言

3つのゲートをすべてクリアした場合のみ、以下の宣言を行うこと：

```
【作業開始ゲート突破宣言】
✅ GATE 1 CLEAR: 保存先確認完了（ユーザー指定: [実際のパス]）
✅ GATE 2 CLEAR: ログファイル作成完了 
✅ GATE 3 CLEAR: 初期記録完了
📝 作業ログパス: [実際のファイルパス]
🚀 作業開始許可: GRANTED
```

## セクション3: 作業ログ作成手順（ステップバイステップ）

### 3.1 保存先の確認とパス決定

**❗ 重要変更点: 保存先は固定されていません**

**手順1: ユーザーへの確認**
```markdown
# 作業ログ保存先の確認

この作業の作業ログ保存先を指定してください。

## 推奨される保存先の種類:

### A. プロジェクト専用
- パス例: `/projects/[project-name]/worklogs/`
- 用途: 特定プロジェクトの作業を一箇所に集約

### B. 機能・タスク別
- パス例: `/features/[feature-name]/logs/`
- 用途: 機能開発単位での作業記録

### C. 日付別（従来方式）
- パス例: `/worklogs/YYYY/MM/` または `/organization-standards/11-worklogs/YYYY/MM/`
- 用途: 時系列での作業記録管理

### D. リポジトリ内
- パス例: `./docs/worklogs/` または `./logs/`
- 用途: コードと同じリポジトリで管理

### E. その他カスタム
- パス例: ユーザー指定の任意のパス
- 用途: 特別な要件に応じた保存

**どの保存先を使用しますか？具体的なパスを教えてください。**
```

**手順2: パス確認と準備**
```bash
# 1. ディレクトリの存在確認
# 2. 必要に応じてディレクトリ作成
# 3. 書き込み権限の確認
# 4. ディスク容量の確認
```

### 3.2 ファイル命名規則（変更なし）

**命名フォーマット:**
```
worklog_YYYYMMDD_HHMMSS_[TASK-ID]_[brief-description].md
```

**具体例:**
```
worklog_20260213_143052_T001_api-design.md
worklog_20260213_143052_PROJ_database-migration.md
worklog_20260213_143052_FIX_critical-bug-fix.md
```

### 3.3 初期記録すべき内容

組織標準テンプレート（`template_worklog.md`）をベースに、以下の最小限の情報を記録：

1. **メタデータセクション**（保存先パス情報を含む）
2. **作業概要**（目的、スコープ、期待成果）
3. **要件理解**（提供された要件の解釈）
4. **作業計画**（大まかな手順とマイルストーン）
5. **参照ドキュメント**（依存する資料とその理由）

**メタデータ記録例:**
```yaml
---
worklog_location: /projects/alpha/worklogs/
save_path_confirmed_by: user
save_path_confirmed_at: 2026-02-13 14:30:52
---
```

## セクション4: 作業中の記録タイミング

| 作業フェーズ | 記録タイミング | 記録すべき内容 | 必須度 |
|------------|-------------|-------------|--------|
| **要件理解** | 要件解釈完了時 | 理解した内容、不明点、仮定事項 | 必須 |
| **設計** | 主要設計決定時 | 設計選択肢、決定理由、トレードオフ | 必須 |
| **実装** | 各機能完了時 | 実装内容、技術選択理由、発生した問題 | 必須 |
| **テスト** | テストケース作成時・実行時 | テスト戦略、結果、発見した不具合 | 必須 |
| **レビュー** | レビュー実施時 | レビュー観点、指摘事項、対応方針 | 必須 |
| **デプロイ** | デプロイ実行前・後 | デプロイ手順、確認項目、結果 | 必須 |
| **問題解決** | 問題発生時・解決時 | 問題内容、原因分析、解決策 | 必須 |
| **作業一時停止** | 中断時 | 現在の状況、中断理由、再開時の注意点 | 必須 |

### 記録更新の頻度ルール

- **リアルタイム更新**: 重要な決定や問題発生時は即座に記録
- **定期更新**: 最低でも30分に1回は進捗を更新
- **フェーズ完了時**: 各作業フェーズ終了時には必ず記録

## セクション5: 作業ログの必須記録項目

### 5.1 最小限必須項目チェックリスト

#### **基本情報**
- [ ] 作業ID（一意識別子）
- [ ] 作業名（明確で理解しやすい名称）
- [ ] 担当AI（モデル名とバージョン）
- [ ] 開始時刻（YYYY-MM-DD HH:MM:SS形式）
- [ ] **保存先パス**（ユーザー指定の実際のパス）
- [ ] **保存先確認日時**
- [ ] 予定完了時刻
- [ ] 実際の完了時刻（作業終了時に更新）

#### **作業内容**
- [ ] 作業目的（何のために行うのか）
- [ ] 作業スコープ（何をやる/やらないの境界）
- [ ] 成功基準（何をもって完了とするか）
- [ ] 前提条件（作業開始時の状況）
- [ ] 制約条件（時間、技術、リソース等の制限）

#### **プロセス記録**
- [ ] 参照した組織標準ドキュメント（パス付き）
- [ ] 使用したツール・技術（バージョン含む）
- [ ] 実行したコマンド・手順（再現可能なレベル）
- [ ] 意思決定の記録（選択肢、判断理由、根拠）
- [ ] 発生した問題と解決策

#### **成果・結果**
- [ ] 作成した成果物（ファイルパス、URL等）
- [ ] 実行結果（成功/失敗、エラーメッセージ）
- [ ] 品質確認結果（テスト結果、レビュー結果）
- [ ] 学習した教訓（良かった点、改善点）

### 5.2 品質チェック項目

作業ログ記録時に以下の品質を確保すること：

- [ ] **具体性**: 曖昧な表現を避け、具体的な内容
- [ ] **再現性**: 他者が同じ作業を実行可能なレベルの詳細さ
- [ ] **客観性**: 事実と意見を明確に分離
- [ ] **時系列**: 作業の流れが時間順に整理されている
- [ ] **完全性**: 作業の全体像が把握できる情報量

## セクション6: エスカレーションルール

### 6.1 作業ログ未作成時の対処

**発生条件**: 作業ログなしで作業を開始してしまった場合

**必須対応**:
1. **即座に作業停止**（現在の作業を中断）
2. **ユーザーに保存先を再確認**
3. **緊急ログ作成**（これまでの作業内容を可能な限り記録）
4. **インシデント報告**（組織標準違反として記録）
5. **作業再開判定**（ログ品質確認後に再開可否決定）

### 6.2 人間への報告・相談が必要な状況

以下の状況では必ず人間の監督者に連絡すること：

- [ ] 保存先をユーザーに確認したが返答がない
- [ ] 指定された保存先にアクセスできない
- [ ] 複数のテンプレートがあり、どれを使用すべきか不明
- [ ] 作業内容が組織標準の想定外で、ログ形式が不適切
- [ ] セキュリティ上の懸念があり、ログ記録が適切でない可能性
- [ ] 作業ログファイルが破損・消失した

### 6.3 AI自己チェック質問リスト

作業開始前に以下の質問に「はい」で答えられない場合は作業開始禁止：

1. ユーザーに保存先を確認し、明確な指定を受けましたか？
2. 作業ログファイルは指定された場所に物理的に存在し、アクセス可能ですか？
3. 初期記録は完了し、必須項目がすべて記入されていますか？
4. 参照すべき組織標準ドキュメントは確認しましたか？
5. この作業の目的と期待成果を明確に理解していますか？
6. 作業中の記録更新計画は立てられていますか？

## セクション7: よくある失敗パターンと対策

### 7.1 典型的な失敗パターン

#### **パターン1: 保存先をユーザーに確認せず、勝手に決める**
- **症状**: 「標準的な場所に保存します」「いつものフォルダに」
- **問題**: ユーザーの意図と異なる場所への保存、管理の混乱
- **対策**: **必ずユーザーに確認**、推測や仮定は禁止
- **予防**: GATE 1での保存先確認を徹底

#### **パターン2: 作業ログを後回しにする**
- **症状**: 「後でまとめて書く」「作業完了後に記録」
- **問題**: 詳細な思考プロセスが失われる
- **対策**: 作業開始前の必須ゲートを厳格に運用
- **予防**: 「今すぐ記録」の習慣化

#### **パターン3: 保存先を確認せずに開始**
- **症状**: 「とりあえず始めて、後で保存先を決める」
- **問題**: ログが行方不明になる、重複作業発生
- **対策**: GATE 1での保存先確認を必須化
- **予防**: ユーザー確認なしでの作業開始を技術的に禁止

#### **パターン4: 作業中断時にログ更新しない**
- **症状**: 作業を止めるときにログを更新しない
- **問題**: 再開時に状況把握に時間がかかる
- **対策**: 中断時の記録を必須化
- **予防**: 自動リマインダーの設置

### 7.2 回復手順

#### **保存先未確認で作業を進めた場合**
1. **即座に作業停止**
2. **ユーザーに保存先確認**（緊急で）
3. **記憶に基づく緊急ログ作成**（これまでの作業内容を記録）
4. **品質評価**（記録内容の完全性・正確性確認）
5. **リスク評価**（情報不足による影響度評価）
6. **継続可否判定**（必要に応じて作業やり直し）

#### **ログファイル破損・消失の場合**
1. **作業即座に停止**
2. **バックアップ確認**（自動バックアップ、履歴確認）
3. **復旧試行**（可能な範囲での復元作業）
4. **代替記録作成**（記憶と成果物から再構築）
5. **再発防止策実施**（バックアップ強化、保存頻度向上）
