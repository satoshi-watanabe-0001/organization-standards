# 🚀 AI実行用クイックリファレンス ★最初に読むこと

## このドキュメントの使い方（AI実行者向け）

### 📖 あなた（AI）がこのドキュメントを使う場面

あなたは**システム開発のタスクを実行する際に、思考プロセスを記録する**必要があります。

このドキュメントは、その記録方法を定めたガイドラインです。

### ⚡ 3ステップ実行ガイド

#### ステップ1: 作業開始前（5分）

1. **セクション2.1の必須セクション構成**を確認
2. あなたが行う作業タイプを特定（要件定義/設計/実装/テスト等）
3. **セクション6の該当する作業例**を1つ読む（記載イメージの把握）

#### ステップ2: 作業実行中（作業時間の10-15%）

1. **セクション2の完全テンプレート**をコピー
2. 各セクションを順に埋める
   - 迷ったら**セクション3の詳細説明**を参照
   - 推論は**必ず3段階以上**記載（セクション3を参照）
   - 確信度を**0-100%で必ず明記**
3. 作業中のメモを随時追記（後でまとめると忘れる）

#### ステップ3: 作業完了後（10-15分）

1. **セクション4.4の評価チェックリスト**で自己チェック
2. 必須項目の記載漏れを確認
3. 推論深度レベル（1-5）を自己評価
4. 推論品質スコアを算出（目標70点以上）

### 🎯 最重要ルール（必ず守ること）

| ルール | 詳細 | 参照先 |
|--------|------|--------|
| **推論の3段階記載** | すべての判断に「なぜそう考えたか」を3段階以上で記載 | セクション2, 3 |
| **確信度の明記** | 主要判断には必ず確信度(0-100%)を記載 | セクション2.1 |
| **複数選択肢の検討** | 意思決定時は3つ以上の選択肢を比較 | セクション3.5 |
| **前作業の継承** | マイルストーン可視化では前作業の思考を継承 | セクション5.2.4 |
| **チェックリスト実施** | 完了時に必ず評価チェックリストを実施 | セクション4.4 |

### 📂 ドキュメントの構造（目次）

| セクション | 内容 | いつ読むか |
|-----------|------|----------|
| **2. 思考アウトプットフォーマット** | 記入すべきテンプレート（コピペして使う） | ✅作業開始時 |
| **3. 各セクションの詳細説明** | 各項目の記入方法の説明 | 🔍作業中に迷ったら |
| **4. 評価基準とチェックポイント** | 品質確認の方法 | ✅作業完了時 |

| **7. 継続的改善サイクル** | 長期的な改善方法 | 📚定期レビュー時 |

### ⏱️ 所要時間の目安

- 作業時間の**10-15%**を思考プロセス記録に充てる
- 例: 6時間の実装作業 → 思考レポート作成に45-60分

### 🎓 記載の良い例 vs 悪い例

**❌ 悪い例**（推論なし）:

```
仮定1: ユーザー数は1万人程度
```

**✅ 良い例**（推論あり）:

```
仮定1: ユーザー数は1万人程度と想定
推論プロセス:
1. 観察事実: 要件に「小規模ECサイト」と記載
2. 類似事例: 過去の小規模ECサイトは平均8,000-15,000人
3. 論理展開: 「小規模」という表現から中央値を想定
4. 結論: 1万人が妥当
確信度: 70%
検証方法: ステークホルダーに確認
```

### 📝 作業タイプ別の重点ポイント

実際の作業では、作業タイプによって記載の重点が異なります。以下を参考に、該当する作業タイプの重点セクションを特に詳細に記載してください。

#### 🎯 要件定義・分析作業

**重点セクション**: 1(要件理解), 5(リスク評価)

**推論の焦点**:
- 不明点・仮定事項の推論プロセスを特に詳細に
- 要件の曖昧さをどう解釈したかの多段階推論
- ステークホルダーの意図の推測プロセス

**記載のコツ**:
- 要件の「書かれていないこと」にこそ推論を集中
- 確信度70%以下の仮定は必ずステークホルダー確認項目に

**所要時間**: 全体の50%を要件理解セクションに

---

#### 🏗️ 設計作業

**重点セクション**: 2(作業分割), 4(意思決定), 5(リスク評価)

**推論の焦点**:
- アーキテクチャ選択の推論(複数案の定量比較)
- 技術選定の推論根拠
- 設計判断のトレードオフ分析

**記載のコツ**:
- 意思決定セクションで必ず3つ以上の選択肢を比較
- 却下した案の「将来再検討の条件」を明記
- 非機能要件(性能、保守性等)への影響を推論

**所要時間**: 全体の40%を意思決定セクションに

---

#### 💻 実装作業

**重点セクション**: 3(情報収集), 4(意思決定), 6(実行過程)

**推論の焦点**:
- ライブラリ・フレームワーク選択の推論
- 実装パターン適用の推論
- 実装中の判断の記録

**記載のコツ**:
- 参照したドキュメント・Stack Overflowの選択理由
- 「なぜこのコードを書いたか」の設計判断を記録
- 迷った実装パターンと選択理由

**所要時間**: 作業中にメモを随時記録、完了後30分で整理

---

#### 🧪 テスト作業

**重点セクション**: 2(作業分割), 5(リスク評価), 7(成果物)

**推論の焦点**:
- テストケース設計の推論
- 優先度付けの推論(何をテストし、何を省略するか)
- バグ原因の推論プロセス

**記載のコツ**:
- テストケース選定の網羅性と効率性のバランス推論
- 発見したバグから推測されるリスクの推論
- カバレッジ目標の設定根拠

**所要時間**: 全体の30%をリスク評価セクションに

---

#### 📚 ドキュメント作成作業

**重点セクション**: 1(要件理解), 7(成果物)

**推論の焦点**:
- 読者・目的の推論
- 情報の粒度・構成の推論
- 説明の順序の推論

**記載のコツ**:
- 「誰が、何のために読むか」の推論を最初に
- 専門用語の使用/説明の判断推論
- 図解の必要性の推論

**所要時間**: 全体の40%を要件理解(読者分析)に

---

#### 🐛 問題解決・デバッグ作業

**重点セクション**: 3(情報収集), 4(意思決定), 6(実行過程)

**推論の焦点**:
- 原因仮説の推論プロセス(複数仮説の検証)
- 調査方法の選択推論
- 解決策選択の推論

**記載のコツ**:
- 仮説検証のプロセスを時系列で記録
- 間違った仮説もなぜそう考えたかを記録(学習材料)
- 再現手順の推論も記載

**所要時間**: 問題解決中にメモを随時記録、解決後20分で整理
